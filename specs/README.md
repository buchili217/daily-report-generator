# 规格目录（Specs）

本目录存放 SDD（规格驱动开发）流程中的需求与设计文档。**先写规格，再写代码**。

## 目录约定

```
specs/
├── README.md
├── 000-template/          # 模板，不直接修改（结构对应指导书附录 B）
│   ├── proposal.md        # 做什么、不做什么、成功标准
│   ├── design.md          # 架构、数据模型、接口契约、ADR
│   ├── tasks.md           # 任务拆解、依赖、并行组
│   └── uml/               # UML 附件（用例图、类图、ER 图等）
└── NNN-<slug>/            # 每个功能一个目录
    ├── proposal.md
    ├── design.md
    ├── tasks.md
    └── uml/
```

- `NNN`：三位递增编号，从 `001` 开始；
- `<slug>`：英文小写、中划线分隔，例如 `001-feishu-calendar-sync`；
- 一个目录对应一次功能迭代，跨多个 PR 时共用同一目录。

## 文件职责

| 文件 | 回答的问题 | 评审要求 |
|---|---|---|
| `proposal.md` | 做什么？不做什么？怎么算完成？ | 必须评审通过才能进入设计 |
| `design.md` | 怎么分层？模块边界？数据模型与接口契约？选型理由（ADR）？ | 技术负责人评审 |
| `tasks.md` | 拆成哪些可执行任务？依赖与并行关系？ | 开发前拆完 |

结构依据课程指导书附录 B：三份 Markdown 规范与 UML 附件同库存放、同流程评审。

## 工作流

1. 复制 `000-template/` 为 `NNN-<slug>/`；
2. 填写 `proposal.md`：范围条目（R-xx）编号、明确"不做什么"、成功标准（SC-xx）可度量；
3. 评审通过后填写 `design.md`：分层架构、模块职责、数据模型、接口契约、ADR（含被否决的备选项）；
4. 绘制 UML 图（用例图、类图、ER 图等）放入 `uml/`，在 `design.md` 第 7 节登记；
5. 拆解 `tasks.md`：一任务 = 一可验证交付物，标注依赖、并行组与验收标准；
6. 开发时每个 PR 引用对应任务编号；规范与代码不一致按缺陷处理；
7. 功能完成后在目录下补充 `notes.md`（可选，记录决策与遗留问题）。

## 状态标记

`tasks.md` 中使用：

- `TODO`：未开始
- `DOING`：进行中
- `DONE`：已完成
- `BLOCKED`：被阻塞（注明原因）
