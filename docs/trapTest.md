## 1. 测试目的与范围

### 1.1 目的

1. 对照《SDD 实战》第 1 章“Vibe Coding 的五大陷阱”，检查本项目在需求、文档、设计、代码、测试、运维环节是否存在同类风险；
2. 用可复现的用例验证 AI 在模糊需求、多轮变更、大段生成、会话丢失、交接维护等场景下的行为；
3. 把每次测试的结论落到 SDD 产物和检查清单上，避免“测完就忘”。

### 1.2 范围

| 维度 | 覆盖 |
|---|---|
| 对象 | 本项目开发中使用的 AI 编程工具（当前登记：Claude Code / `deepseek-flash`；其他成员工具待登记） |
| 环节 | 需求澄清、文档编写、架构设计、任务拆解、代码生成、测试、交接 |
| 阶段 | 第 1 周已完成“文档与仓库审计”；第 2 周起执行“代码阶段交互测试” |
| 不覆盖 | 产品运行时 LLM 的输出质量（另见日报生成验收标准，不属于本报告的开发工具测试） |

### 1.3 方法与证据

- **方法**：陷阱自查 + 仓库审计 + 交互式测试（同一提示词重复执行、对照规范检查输出）+ 人工复核；
- **证据**：仓库文件与行号、git 提交记录、AI 使用日志、对话/提示词记录（如有）、测试用例执行记录；
- **判定**：通过 / 部分通过 / 未通过 / 不适用；判定必须附证据，不允许只写结论。

## 2. 五大陷阱基线

| 编号 | 陷阱 | 定义（据《SDD 实战》第 1 章） | 典型信号 | 直接后果 |
|---|---|---|---|---|
| T1 | 需求蒸发 | 重要决策只存在于对话中，未持久化为规范 | 关闭会话后没人说得清“为什么这么做” | 返工、范围蔓延 |
| T2 | 上下文漂移 | 多轮对话中约束逐轮丢失，产出与初始需求只剩字面相似 | 越改越偏、文档互相矛盾 | 功能与目标脱节 |
| T3 | 不可审查 | AI 一次生成大量代码，无取舍说明，review 无从切入 | diff 巨大、无注释/无设计说明 | 缺陷与安全风险入库 |
| T4 | 不可复现 | 同一提示词两次结果不同，会话丢失后无法还原 | 无法解释某行代码从何而来 | 缺陷无法定位、无法回归 |
| T5 | 不可维护 | 缺 ADR、接口契约、模块边界，后人只能推倒重来 | 新人靠猜、改一处坏一片 | 技术债累积 |

> **来源核对**：① 黄佳《SDD 实战：规范驱动开发之道》第 1 章；② 课程指导书第 1 周任务 1 与附录 E；③ 公开书评/读书笔记对五陷阱的转述。三者在“需求蒸发/上下文漂移/不可审查/不可复现/不可维护”的名称与含义上一致，详见附录 A。

### 2.1 个人陷阱自查（对照本项目）

对照五大陷阱，本项目的文档阶段实际出现过以下问题，均有仓库证据：

- **T1 需求蒸发**：`proposal.md` 的交付物路径按模板写成 `docs/spec.md` 等，未对照仓库实际结构；需求决策此前只散落在文档里，没有一问一答记录。本次通过新增 `docs/需求澄清报告.md` 和路径审计补齐。
- **T2 上下文漂移**：`proposal.md` §5 与 §12 对“团队汇总”的范围口径不一致；技术栈写 Python 3.11，而课程准备清单要求 3.12+；合规表述“数据全程在租户内”与调用第三方模型 API 冲突。
- **T3 不可审查**：当前尚无业务代码，暂不适用；但文档初稿缺少逐条来源，已通过本报告与 AI 使用声明的三源核验表补强。
- **T4 不可复现**：2026-11-03 初稿阶段的 AI 使用情况与会话记录未留存（是否使用 AI 待作者确认），无法还原当时的提示词与模型版本；已建立 AI 使用日志，并要求后续重要会话留痕。
- **T5 不可维护**：选型文档有对比与理由，但没有 ADR 编号和接口契约；新人只能读长文，不能快速定位“为什么这样选”。第 2 周补 ADR 与 `design.md`。

> 如作者另有课程外的历史案例，可在本节补充“当时场景—踩中的陷阱—后果—现在的做法”；不得编造。以上五条均可在本仓库或本次审计记录中复核。

### 4.3 重点发现说明

#### F-01 交付物路径与仓库实际结构不一致（T2）

- **现状**：`proposal.md` §7 写 `docs/proposal.md`、`docs/spec.md`、`docs/plan.md`、`docs/tasks.md`；§12 又要求产出 `docs/spec.md`。
- **实际**：`proposal.md` 在仓库根目录；需求/设计/任务模板在 `specs/000-template/`；尚无 `specs/001-*`。
- **影响**：评审按 proposal 找文件会扑空；AI 后续生成可能把规范写到错误目录。
- **建议**：统一为“根目录 `proposal.md` + `specs/NNN-<slug>/{spec,plan,tasks}.md`”，并在 `README.md` 文档索引中补链接。

#### F-02 范围口径不一致（T2）

- **现状**：`proposal.md` §5 列“团队汇总”为 P1；§12 只承诺 P0 + Git 采集。
- **影响**：验收时对“是否交付团队汇总”产生争议。
- **建议**：明确“v1 必须：P0 + Git；团队汇总：P1，若第 2 周进度允许则交付最小版（成员日报列表 + 阻塞项标记），否则列入阶段二/后续迭代”，并同步到 proposal §5/§12。

#### F-03 合规表述冲突（T2/T5）

- **现状**：proposal 称数据全程在企业租户内流转；架构默认 DeepSeek API。
- **影响**：答辩/合规评审时可能被质疑虚假承诺。
- **建议**：改为准确表述，并给出三种部署模式：公有云 API（数据最小化、不用于训练）、专有云/私有化（数据不出域）、本地模型（完全不出域）；在隐私政策中写清。

#### F-04 仓库边界不清（T5）

- **现状**：父仓库未跟踪 `daily-report-generator/`，该目录自带 `.git` 且与父仓库同 remote。
- **影响**：代码可能提交到错误仓库；父仓库看不到子仓库内容；CI/评审混乱。
- **建议**：二选一——删除子仓库 `.git` 并将内容纳入父仓库；或正式改为 submodule 并在 `README.md` 说明。

> 以上发现均为文档/仓库层面可复核的事实，不涉及对 AI 输出质量的臆测。修复后应在“整改记录”中更新状态。

## 7. 结论

1. **当前阶段最突出的风险是 T4（不可复现）和 T2（上下文漂移）**：仓库尚无 AI 会话日志，且已发现 4 处文档口径不一致；这两类问题在代码阶段会被放大。
2. **T1 已明显缓解**：proposal 已有范围/非目标/可度量指标，本次补齐需求澄清报告后，需求决策可追溯。
3. **T5 处于“部分缓解”**：有选型对比，但缺 ADR、`design.md`、接口契约；第 2 周必须补齐。
4. **T3 当前不适用**：尚无业务代码；代码阶段必须坚持小步提交与逐 diff 审查。
5. **优先整改项**：F-01 路径、F-02 范围、F-03 合规表述、F-04 仓库边界、A-10 配置占位；建议在第 1 周末前完成文档类整改，第 2 周设计阶段完成 ADR 与 `design.md`。
