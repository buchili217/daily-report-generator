# 架构与技术栈选型

> 项目：智能日报生成器（基于飞书开放平台 + 大语言模型）
> 用途：课程设计——《软件工程职业技能实践课程设计指导书（SDD 与 AI 编程工具版）》

## 一、架构选型

| 维度 | 模块化单体 + 异步任务（推荐） | 微服务 | Serverless / 云函数 | 单机脚本 + 定时任务 |
|---|---|---|---|---|
| 开发成本 | 低，一个仓库、一套部署 | 高，服务拆分、接口、联调 | 中，需适配平台限制 | 极低 |
| 部署运维 | 简单，Docker Compose 即可 | 复杂，需要注册中心、网关、可观测体系 | 低，但受平台约束 | 最简单，但不可扩展 |
| 性能 | 足够（I/O 密集场景） | 可独立扩容 | 冷启动延迟 | 单点瓶颈 |
| 扩展性 | 中，模块边界清晰即可拆分 | 高 | 中 | 低 |
| 故障隔离 | 中（进程内） | 高 | 高 | 无 |
| 适合场景 | 课程设计、10–500 人团队产品 | 大团队、多产品线 | 事件驱动的小功能 | 个人工具、原型 |
| 主要风险 | 模块耦合随时间退化 | 过度设计、运维成本失控 | 定时/长任务受限、厂商锁定 | 无法支撑多人并发 |

### 各方案优缺点

**模块化单体（推荐）**

- 优点：一次部署、调试简单；模块内按"采集 / 生成 / 推送 / 汇总"划分边界，后续可按需拆出；团队小、周期短时效率最高。
- 缺点：所有模块共享进程与数据库，单点故障影响面大；若边界管理不严，容易退化为"大泥球"。

**微服务**

- 优点：独立部署、独立扩容、故障隔离；适合数据采集与 LLM 生成负载差异大的场景。
- 缺点：课程设计周期内成本过高；分布式事务、链路追踪、配置管理都是额外负担；团队规模小于 5 人时收益为负。

**Serverless / 云函数**

- 优点：免运维、按量计费、天然弹性；适合"每天定时触发一次"的采集任务。
- 缺点：冷启动影响生成时延；执行时长受限（大模型长文本生成可能超时）；飞书回调调试不便；平台锁定。

**单机脚本 + 定时任务**

- 优点：最快出原型，适合验证"能不能生成"。
- 缺点：无法多用户、无权限体系、无持久化查询，不能作为课程设计交付形态。

### 推荐架构：模块化单体 + 适配器模式 + 异步任务队列

```
飞书开放平台/前端 ──> 接入层 (HTTP API / 事件回调 / 机器人)
                          │
                  ┌───────┼────────────┐
              认证与权限  日报编排服务  推送服务
                  │        │            │
                  └──── 领域服务层 ─────┘
                数据源适配器 | LLM Provider | 模板引擎 | 汇总服务
                          │
             PostgreSQL（业务+原始数据） / Redis（缓存+队列）
                          │
                   Celery Worker / Beat（定时采集与生成）
```

选择理由：系统的负载特征是 **I/O 密集**（调飞书 API、调模型 API），不是计算密集；瓶颈在外部接口而非自身吞吐，单体 + 异步队列足以支撑目标规模，且能在一学期内完成并讲清楚。

## 二、技术栈对比

### 2.1 后端语言与框架

| 选项 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **Python + FastAPI** | 开发效率高；原生异步适合大量外部 API 调用；飞书官方有 `lark-oapi` Python SDK；LLM 生态最完整（各家 SDK、LangChain 等）；pytest 测试简单 | 弱类型，需 mypy 兜底；GIL 限制 CPU 密集任务（本项目不涉及）；部署需 uvicorn/gunicorn | **推荐** |
| Java + Spring Boot | 企业级生态成熟；类型安全；学校课程常用；事务与并发控制强 | 代码量大、启动慢；飞书/LLM 第三方 SDK 生态较弱；课程设计周期内开发速度偏慢 | 指导书要求 Java 时选 |
| Node.js + NestJS | 前后端同语言；事件驱动模型天然适合回调；飞书 Node SDK 可用 | CPU 密集任务弱；异步错误处理易失控；类型体系依赖 TS 工程化 | 前端团队为主时可选 |
| Go + Gin | 性能好、部署单文件、并发模型清晰 | 开发效率低于 Python；LLM/飞书 SDK 生态最弱；课程设计收益不明显 | 不推荐 |

### 2.2 数据库

| 选项 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **PostgreSQL** | JSONB 适合存原始采集数据（结构不固定）；事务、索引、全文检索齐全 | 运维比 SQLite 重；需要额外容器 | **推荐** |
| MySQL | 普及度高、教程多、学校常用 | JSON 支持较弱；全文检索能力一般 | 可平替 |
| MongoDB | 文档模型天然适合原始日志与采集快照 | 关联查询弱；事务能力不如关系库；与业务表的统计汇总配合差 | 可作为原始数据旁路 |
| SQLite | 零运维、单文件、适合原型与本地测试 | 并发写入弱；不适合多用户部署 | 仅本地开发 |

### 2.3 缓存与任务队列

| 选项 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **Redis + Celery** | 成熟稳定；支持定时任务（Beat）、重试、限流；与 FastAPI 集成方案多 | Celery 配置与调试偏重；Windows 本地运行需注意（建议 Docker） | **推荐** |
| Redis + ARQ / RQ | 轻量、原生 asyncio、代码少 | 生态小、文档少；定时任务能力弱于 Celery Beat | 轻量替代 |
| APScheduler（进程内） | 零额外组件，几行代码搞定定时 | 多实例部署会重复执行；无重试与任务持久化 | 仅单实例原型 |
| RabbitMQ / Kafka | 消息可靠性、削峰能力强 | 本项目量级用不上；运维成本高 | 过度设计 |

### 2.4 大模型接入

| 选项 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **国内模型（DeepSeek / 通义千问 / 豆包）** | 中文效果好；价格低；境内调用无数据出境合规问题；延迟低 | 复杂推理能力略逊于头部海外模型；部分模型限流 | **默认** |
| 海外模型（OpenAI / Claude） | 生成质量与指令遵循最好 | 数据出境合规风险；网络稳定性；成本较高 | 作为可切换选项 |
| 自部署开源模型（Qwen / Llama） | 数据完全不出域；可私有化交付 | 需要 GPU 算力；运维与调优成本高 | 企业版/私有化场景 |

**做法**：抽象 `LLMProvider` 接口（`generate(prompt, schema) -> text`），配置层切换模型，业务代码不感知厂商。这既是架构上的适配器模式，也是选型风险的隔离手段。

### 2.5 前端

| 选项 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **Vue 3 + TS + Vite + Element Plus** | 上手快、国内资料多；组件库完整；构建快 | 生态略小于 React | **推荐**（管理端） |
| React + TS + Vite + Ant Design | 生态最大；组件丰富；社区资源多 | 概念多（Hooks/状态管理）；初期学习曲线 | 平替 |
| 飞书网页应用 / H5 内嵌 | 免独立登录（复用飞书身份）；贴近用户工作流；移动端可用 | 调试依赖飞书客户端；受平台容器限制 | **员工端推荐** |
| 纯机器人消息卡片（无前端） | 开发量最小；交互在飞书内完成 | 复杂编辑体验差；无法做汇总看板 | 可作为 MVP 降级方案 |

### 2.6 部署与运维

| 选项 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **Docker Compose 单机** | 环境一致、一键启动、可复现；答辩演示方便 | 无高可用；扩容需手工 | **推荐** |
| 云服务器裸部署 | 简单直接 | 环境漂移、依赖冲突 | 不推荐 |
| Kubernetes | 弹性、自愈、滚动发布 | 学习与运维成本远超项目规模 | 过度设计 |
| 云托管 PaaS（云函数 + 托管数据库） | 免运维 | 成本不透明、调试受限 | 备选 |

### 2.7 其他组件

| 组件 | 选项 | 优点 | 缺点 |
|---|---|---|---|
| 认证 | 飞书 OAuth 2.0 + JWT 会话 | 免密登录、贴合场景 | 依赖飞书可用性；本地调试需 mock |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic | 成熟、类型提示友好 | 学习成本中等 |
| 测试 | pytest + httpx + pytest-asyncio | 生态成熟、异步支持好 | 需自行搭建飞书/模型 mock |
| 代码质量 | ruff + mypy + pre-commit | 快、统一风格、提前发现类型错误 | 初期配置耗时 |
| 可观测 | structlog + Prometheus + Grafana | 结构化日志、指标可查 | 课程设计可简化为日志 + 简单看板 |
| CI/CD | GitHub Actions | 免费、配置简单 | 国内网络需代理 |

## 三、推荐组合

| 层次 | 选型 |
|---|---|
| 架构 | 模块化单体 + 适配器 + 异步任务队列 |
| 后端 | Python 3.11 + FastAPI + Pydantic |
| 数据 | PostgreSQL + SQLAlchemy 2.0 + Alembic |
| 缓存/队列 | Redis + Celery（Worker + Beat） |
| 大模型 | 统一 Provider 接口，默认国内模型，可切换 |
| 员工端 | 飞书消息卡片 + H5（内嵌飞书） |
| 管理端 | Vue 3 + TypeScript + Vite + Element Plus |
| 部署 | Docker Compose + Nginx |
| 质量 | pytest + ruff + mypy + GitHub Actions |

**不选微服务与 K8s 的核心理由**：本项目的复杂度来自外部系统集成（飞书权限、数据清洗、模型输出稳定性），而不是内部服务拆分；在课程设计周期内，微服务只会增加联调与运维成本，不产生对应收益。

## 四、若指导书有硬性要求

- **要求 Java**：Spring Boot 3 + MyBatis-Plus/JPA + Redis + Quartz + Vue 3，架构不变，仅替换实现层；
- **要求前后端分离且指定框架**：前端按其要求，后端保持模块化单体；
- **要求纯前端/无后端**：降级为"飞书消息卡片 + 云函数定时触发"，但会失去团队汇总与历史检索能力，需在报告中说明取舍。
