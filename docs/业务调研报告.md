# 《智能日报生成器》业务调研报告

## 摘要

日报是团队同步进展、暴露风险、沉淀过程资产的基础管理动作，但"写日报"长期存在耗时高、内容流于形式、数据来源分散、管理层难以汇总等问题。本项目拟基于**飞书开放平台 + 大语言模型**，构建一款"零录入"的智能日报生成器：自动采集员工在飞书（日历、文档、任务、群聊）及研发工具（Git、Jira 等）中的工作痕迹，经清洗聚合后由大模型生成结构化日报，员工确认或微调后一键推送，管理者侧自动汇总团队日报。本报告通过桌面研究、用户访谈设计与竞品体验，论证该产品的市场需求、目标用户、竞品格局、功能范围与商业可行性，结论是：**需求真实、技术可行、建议以飞书生态内中小企业与研发团队为切入点，先做 MVP 再逐步扩展数据源**。

> 说明：本报告基于《软件工程职业技能实践课程设计指导书（SDD 与 AI 编程工具版）》的课程设计要求撰写。文中标注【待实测】的数据需在正式调研完成后替换为真实问卷/访谈结果。

## 一、调研概述

### 1.1 项目背景

1. **管理侧**：团队规模超过 10 人后，管理者难以靠口头同步掌握全局，日报成为低成本的过程可视化手段；但员工提交的日报质量参差、格式不一，汇总和追踪成本高。
2. **员工侧**：写日报本质是"回忆 + 组织语言"，多数人每天花费 10–30 分钟，且容易遗漏当天真实产出；连续加班或跨项目时尤为抵触。
3. **技术侧**：大模型已具备较强的摘要、结构化与改写能力；飞书等协作平台开放了日历、文档、任务、消息、多维表格等 API，使"从工作痕迹自动还原工作内容"第一次具备工程可行性。
4. **合规侧**：《数据安全法》《个人信息保护法》对企业内部数据的使用提出明确要求，产品必须在"数据不出企业、最小必要、可审计"的前提下设计。

### 1.2 调研目的

- 验证"自动生成日报"是否为真实、高频、可付费的需求；
- 明确目标用户、使用场景与核心痛点优先级；
- 摸清竞品能力边界，找到差异化定位；
- 输出可支撑后续需求规格（Spec）与架构设计的功能清单与约束条件。

### 1.3 调研方法

| 方法 | 对象/范围 | 产出 |
|---|---|---|
| 桌面研究 | 行业报告、飞书/钉钉开放平台文档、竞品公开资料 | 市场趋势、竞品功能矩阵 |
| 用户访谈 | 研发、产品、运营、团队负责人各 2 人，共 8 人【待实测】 | 痛点、场景、现有替代方案 |
| 问卷调查 | 目标企业员工，目标回收 60 份以上【待实测】 | 痛点分布、付费意愿 |
| 竞品体验 | 飞书汇报、钉钉日志、企业微信汇报、Notion AI、通用大模型 | 功能对比与差距分析 |

### 1.4 调研假设与范围

- 假设目标客户为 10–500 人的中小企业/团队，已使用飞书或愿意迁移；
- 首期只做"生成 + 确认 + 推送"闭环，不做考勤绩效评价，避免触碰敏感管理场景；
- 数据源首期覆盖飞书内部数据与 Git 提交记录，Jira/禅道等作为二期扩展。

## 二、市场与行业分析

### 2.1 行业趋势

1. **AI 办公从"助手"走向"代理"**：早期 AI 办公产品以问答、润色为主，2024 年后逐步转向自动执行任务（自动写周报、会议纪要、待办提取）。日报生成属于典型的"高频、低创造性、可自动化"场景，适合作为 AI Agent 的落地切口。
2. **协作平台开放生态成熟**：飞书开放平台提供事件订阅、机器人、消息卡片、云文档、日历、任务、通讯录、多维表格等能力，第三方应用可以较低成本嵌入用户的日常工作流。
3. **企业数据治理趋严**：企业在引入 AI 工具时普遍关注数据是否出域、能否私有化部署，这为"基于企业自身数据、可控可审计"的垂直工具留下空间。
4. **大模型调用成本快速下降**：单次日报生成的 token 成本已降至可忽略量级（见 7.2），使"每人每天自动生成"在经济上成立。

### 2.2 目标市场与用户规模

- **核心市场**：已使用飞书的中小企业与研发团队。公开资料显示我国中小企业数量超过 5000 万户，协同办公 SaaS 渗透率持续提升，其中研发型团队对日报、周报的刚需最强。
- **次级市场**：使用钉钉/企业微信的团队（需做平台适配）、远程与分布式团队、外包与项目制团队。
- **机会判断**：整体市场不需要精确测算即可判断——日报是普遍存在的管理动作，而现有产品多以"手工填写 + 表单收集"为主，自动化程度低，存在明确的产品空位。

### 2.3 政策与合规环境

- 《数据安全法》《个人信息保护法》《网络安全法》要求处理员工工作数据时遵循最小必要、告知同意、目的限定原则；
- 企业侧普遍要求数据不出域、可审计、可删除；
- 因此产品需支持：字段级脱敏、按部门/项目隔离权限、生成记录留存与审计日志、私有化/专有云部署选项。

### 2.4 市场机会小结

需求普遍存在 + 现有方案自动化不足 + 平台能力已就绪 + 成本可接受，构成本项目的市场机会窗口。竞争的关键不在于"能不能生成"，而在于**数据采集的完整度、生成内容的可信度、以及与企业现有工作流的融合度**。

## 三、用户研究

### 3.1 用户画像

| 角色 | 特征 | 核心诉求 | 使用频率 |
|---|---|---|---|
| 一线员工（研发/产品/运营） | 22–35 岁，日常在飞书与研发工具中工作 | 少花时间写日报，内容真实不漏项 | 每日 |
| 团队负责人 | 管理 5–20 人 | 快速掌握进展与风险，减少催收 | 每日 |
| 部门/HR 管理者 | 关注汇总与合规 | 统一格式、可导出、可追溯 | 每周/每月 |

### 3.2 典型场景

1. **下班前 10 分钟**：员工打开工具，系统已根据当天的日历会议、文档编辑、任务变更、Git 提交生成日报草稿，员工补充"明日计划"后推送。
2. **项目复盘**：负责人查看团队日报自动汇总，识别阻塞项与跨人依赖。
3. **远程/跨时区团队**：异步同步进展，减少会议。
4. **新人/轮岗**：通过历史日报快速了解项目脉络。

### 3.3 痛点归纳

| 编号 | 痛点 | 影响 | 现有替代方案及其不足 |
|---|---|---|---|
| P1 | 回忆当天工作耗时 | 每天 10–30 分钟 | 翻聊天记录、看提交记录，效率低 |
| P2 | 数据来源分散 | 容易漏项、内容不完整 | 手工拼接多个系统截图 |
| P3 | 格式不统一 | 管理者汇总困难 | 强制模板，员工抵触 |
| P4 | 日报形式化 | 内容空泛，失去管理价值 | 无有效手段 |
| P5 | 隐私顾虑 | 不愿暴露全部工作细节 | 拒绝使用或敷衍填写 |

> 上述痛点排序需在访谈与问卷完成后用数据校准【待实测】。

### 3.4 需求优先级（MoSCoW）

- **Must**：多源数据采集、AI 生成、人工编辑确认、定时推送、权限控制；
- **Should**：团队汇总视图、模板定制、历史检索、多语言；
- **Could**：周报/月报自动生成、风险预警、与 OKR 关联；
- **Won't（首期）**：绩效评分、员工行为监控、跨企业数据对比。

## 四、竞品分析

| 产品 | 数据来源 | 自动化程度 | 生成质量 | 部署/隐私 | 主要不足 |
|---|---|---|---|---|---|
| 飞书汇报/日报 | 手工填写 | 低 | 取决于员工 | SaaS | 无自动采集，仍靠人工 |
| 钉钉日志 | 手工填写 + 模板 | 低 | 取决于员工 | SaaS | 同上，生态绑定钉钉 |
| 企业微信汇报 | 手工填写 | 低 | 取决于员工 | SaaS | 同上 |
| Notion AI / 语雀 AI | 文档内容 | 中 | 较好 | SaaS | 依赖文档沉淀，不覆盖日历/任务/代码 |
| 通用大模型（ChatGPT/通义/文心） | 用户粘贴 | 低 | 好 | 数据出域 | 需手工喂数据，企业合规风险 |
| 开源日报机器人 | 单一源（如 Git） | 中 | 一般 | 可自部署 | 数据源单一，缺少产品化体验 |

**结论**：现有竞品的空白在于"**多源自动采集 + 企业内闭环 + 可编辑可信**"。飞书生态内尚无成熟的原生自动日报产品，本项目可定位为"飞书工作流的智能日报外挂"：不替代飞书，而是把飞书里的工作痕迹变成日报。

## 五、产品定位与需求范围

### 5.1 价值主张

> 对**每天要写日报的员工**：不用回忆、不用翻记录，10 秒确认即可提交；
> 对**团队负责人**：每天自动收到结构化团队进展与风险提示；
> 对**企业**：数据留在企业内，生成过程可审计。

### 5.2 功能需求（首期 MVP）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| FR-01 | 飞书账号登录与授权 | OAuth 授权，按需申请日历/文档/任务/消息权限 | P0 |
| FR-02 | 日历与会议采集 | 读取当天日程、会议主题与参与人 | P0 |
| FR-03 | 文档与任务采集 | 当天编辑的文档、完成/变更的任务 | P0 |
| FR-04 | Git 提交采集 | 按仓库/分支聚合 commit、PR | P1 |
| FR-05 | AI 日报生成 | 按模板生成"今日完成/进行中/风险/明日计划" | P0 |
| FR-06 | 草稿编辑与确认 | 支持增删改、字段开关、重新生成 | P0 |
| FR-07 | 推送与归档 | 推送到指定群/个人，存档可检索 | P0 |
| FR-08 | 团队汇总 | 负责人查看成员日报汇总与阻塞项 | P1 |
| FR-09 | 权限与脱敏 | 部门隔离、敏感字段过滤、审计日志 | P0 |
| FR-10 | 模板管理 | 团队自定义日报模板与生成规则 | P2 |

### 5.3 非功能需求

- **性能**：单份日报生成 ≤ 5 秒，采集任务在后台异步完成；
- **可用性**：生成失败可降级为"空白模板 + 提示"，不阻断提交；
- **安全**：最小权限授权、数据传输与存储加密、审计日志留存 ≥ 90 天；
- **可扩展**：数据源以适配器模式接入，便于扩展 Jira、禅道、GitLab；
- **合规**：支持关闭个人数据采集、支持删除与导出。

## 六、业务流程设计

**主流程**：

`定时触发/手动触发 → 多源数据采集 → 清洗与聚合 → 大模型生成草稿 → 员工确认/编辑 → 推送与归档 → 团队汇总`

| 阶段 | 用户动作 | 系统动作 | 关键指标 |
|---|---|---|---|
| 采集 | 无感 | 拉取日历/文档/任务/提交 | 采集成功率、延迟 |
| 生成 | 点击"生成"或自动 | 组装上下文、调用模型 | 生成耗时、采纳率 |
| 确认 | 编辑、确认 | 保存版本、记录修改 | 平均修改字数 |
| 推送 | 一键发送 | 消息卡片推送、归档 | 提交率 |
| 汇总 | 负责人查看 | 聚合、识别阻塞 | 查看率、催收次数下降 |

## 七、可行性分析

### 7.1 技术可行性

- **平台能力**：飞书开放平台具备所需 API 与机器人/消息卡片能力，权限可按应用申请；
- **模型能力**：结构化摘要与改写是当前大模型的成熟能力，配合模板与少样本示例可稳定输出；
- **工程复杂度**：核心难点在数据采集的权限与清洗，而非模型本身；采用适配器 + 任务队列即可控制复杂度；
- **风险点**：平台 API 限流、权限审核周期、消息内容合规。

### 7.2 经济可行性（估算）

- 单份日报约消耗 2–4k tokens，按国产模型价格估算，单份成本约 0.002–0.01 元；
- 100 人团队、每月 22 个工作日，模型成本约 5–25 元/月，远低于节省的人力成本（按每人每天节省 15 分钟计）；
- 开发成本以课程设计团队人力为主，服务器与 API 费用可控。

### 7.3 运营可行性

- 推广路径：种子团队试点 → 部门内推广 → 全公司；
- 关键动作：首周人工陪跑、模板共创、展示"节省时间"的可量化收益；
- 阻力来源：担心被监控、担心生成内容失真，需通过透明授权与可编辑机制化解。

### 7.4 合规可行性

- 遵循最小必要原则，仅采集与工作产出直接相关的数据；
- 员工可在生成前查看"系统读取了哪些数据"，并支持单条排除；
- 企业管理员可配置数据保留期与脱敏规则。

## 八、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 生成内容失真/幻觉 | 编造未完成的工作 | 强制引用来源、只基于采集事实生成、必须人工确认 |
| 隐私与信任 | 员工抵触、担心监控 | 透明授权、字段级开关、明确"用于生成日报而非绩效" |
| 平台依赖 | 飞书 API 变更/限流 | 抽象适配层，预留钉钉/企微适配 |
| 采集不完整 | 漏掉线下工作 | 提供手动补充入口，生成前提示数据覆盖度 |
| 成本失控 | 调用量突增 | 缓存、按需触发、小模型路由 |
| 使用率低 | 试点后弃用 | 降低操作步骤至 1–2 步，推送时机贴合下班前习惯 |

## 九、结论与建议

1. **需求成立**：日报是高频刚需，现有产品自动化程度低，"零录入"具备明确价值。
2. **定位建议**：以飞书生态内的中小企业与研发团队为首发市场，做"工作痕迹 → 日报"的自动化工具，不与协作平台正面竞争。
3. **MVP 范围**：飞书日历/文档/任务采集 + AI 生成 + 编辑确认 + 推送，先跑通单人闭环，再补团队汇总。
4. **关键成功指标**：日报提交率、平均编辑字数（越少越好）、生成采纳率、负责人查看率、催收次数下降幅度。
5. **下一步**：完成实测问卷与访谈 → 输出需求规格说明（Spec）→ 原型与技术验证（飞书 API + 模型调用）→ 小范围试点。
