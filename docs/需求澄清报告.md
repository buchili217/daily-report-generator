> 项目：智能日报生成器（Smart Daily Report Generator）
> 关联：课程指导书第 1 周任务 2；`proposal.md`；`docs/业务调研报告.md`；`docs/架构与技术栈选型.md`

> 版本：v1.0　|　日期：2026-11-06　|　状态：待项目组评审

## 1. 概述

### 1.1 目的

把“团队日报”场景中的模糊表述逼成可执行、可验收的需求，回答三个问题：

1. **到底为谁做**：员工、团队负责人、部门/HR、系统管理员分别要什么、不能看到什么；
2. **到底做什么**：数据源、日报粒度、归属规则、推送方式、失败处理、合规边界；
3. **怎么算做完**：每条需求对应哪个功能、哪条验收标准、哪个指标。

本报告同时记录 AI 结构化提问与项目组回答的过程，作为 `proposal.md` 的输入和质量证据。

### 1.2 澄清对象与角色

| 角色 | 核心关注点 | 在澄清中的职责 |
|---|---|---|
| 一线员工（研发/产品/运营） | 少花时间、内容真实、隐私可控 | 回答使用场景、隐私边界、编辑习惯 |
| 团队负责人 | 快速掌握进展与阻塞、减少催收 | 回答汇总粒度、权限范围、阻塞项定义 |
| 部门/HR 管理者 | 统一格式、可导出、可追溯 | 回答归档周期、导出格式、审计要求 |
| 系统管理员 | 采集源、模板、保留期、审计可配置 | 回答配置项、故障处理、运维边界 |
| 飞书租户管理员 | 应用授权、数据范围审批 | 回答授权流程、最小权限、测试企业 |
| 项目组 | 范围、进度、技术可行性 | 决策、记录、评审 |

> “系统管理员”和“飞书租户管理员”是澄清中新增的隐含角色：原 `proposal.md` 只列了三类用户，但飞书授权、审计、数据保留需要明确责任人，否则 P0 的“权限与脱敏”无法落地。

### 1.3 方法与过程

1. AI 依据现有项目文档和“团队日报”场景，生成 20 个澄清问题（正文收录 18 个，未纳入的 2 个见附录 A）；
2. 项目组按角色逐条回答：能由现有文档确定的，标注来源；不能确定的，列为开放问题；
3. 对回答做四类冲突检查：范围冲突、合规冲突、技术冲突、验收冲突；
4. 从问答中归纳隐含需求，映射到功能编号与验收标准；
5. 形成本报告，评审通过后更新 `proposal.md`，并创建 `specs/001-*/spec.md`。

> **说明**：本报告的提问与整理由 AI 辅助完成，回答与决策由项目组确认；标注【待确认】的条目尚未形成最终决策，不作为验收依据。

### 1.4 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | 课程指导书、`proposal.md`、`docs/业务调研报告.md`、`docs/架构与技术栈选型.md`、仓库现有配置 |
| 输出 | 18 条问答记录（Q-01～Q-18）、5 个痛点的系统解法（痛点 P1～P5）、14 条隐含需求（H-01～H-14）、范围确认、冲突取舍、开放问题 |
| 后续 | 更新 proposal、创建 `specs/001-daily-report-mvp/spec.md`、第 2 周 `plan.md`/`tasks.md`/ADR |

## 2. 业务场景与角色确认

### 2.1 主流程

`定时/手动触发 → 多源采集 → 清洗与聚合 → LLM 生成草稿 → 员工确认/编辑 → 推送与归档 → 团队汇总`

### 2.2 角色与权限边界

| 角色 | 能做什么 | 不能做什么 | 数据可见范围 |
|---|---|---|---|
| 一线员工 | 查看/编辑/确认/推送本人日报；查看采集来源；关闭字段；导出/删除本人数据 | 查看他人日报；关闭审计 | 本人 |
| 团队负责人 | 查看直属成员日报与汇总；标记阻塞项 | 查看非直属成员；导出全公司 | 直属团队 |
| 部门/HR 管理者 | 按周期导出/归档；查看合规审计 | 修改员工日报；用日报做绩效排名 | 授权部门 |
| 系统管理员 | 配置采集源/模板/保留期；查看审计元数据 | 默认不能查看日报正文（除非单独授权） | 配置与审计元数据 |
| 飞书租户管理员 | 授予应用权限；审批数据范围 | 直接操作业务数据 | 租户级授权 |

> 权限原则：默认不可见、最小必要、可审计；跨团队/跨部门默认隔离。

### 3.2 关键问答详述

#### Q-01 数据源：为什么首期不采集群聊？

群聊消息包含大量与工作产出无关的闲聊、表情、转发和敏感信息，且“谁贡献了什么”很难从消息流中可靠归属。首期采集日历、云文档、任务和 Git 已能覆盖“会议、文档产出、任务进展、代码提交”四类主要工作痕迹；群聊消息列为 P2 候选，若课程要求纳入，则按“仅采集与本人相关且被 @ 的消息、生成前可逐条排除”的最小化方案执行。

> 与指导书示例的差异：指导书第 1 周示例把“飞书消息”列为本期采集范围。本项目选择不采集，需在 proposal 的“不做什么”中说明理由，并由教师确认是否接受。

#### Q-04 协作成果归属：自动 + 人工确认

自动归属不可能 100% 准确。本项目的策略是：

1. **高置信度**（文档 owner、任务负责人、commit author）：自动写入草稿，并显示来源；
2. **中置信度**（文档协作者、会议参与人、PR reviewer）：写入“可能参与”区，由员工勾选确认；
3. **低置信度/无法判断**：不写入，提供手动补充入口；
4. 所有归属都保留来源引用，员工可排除；排除后不进入日报。

这样既避免“漏掉协作成果”，也避免“把他人成果算给本人”造成的信任问题。

#### Q-05/Q-06/Q-07 隐私、可信与降级

三者是同一个信任链条：

- **采集前**：让员工看到“系统读取了哪些数据”，支持单条排除；
- **生成时**：只基于事实、每条带来源、无来源不生成；
- **生成后**：必须人工确认；失败时降级为空白模板，不阻断提交；
- **长期**：明确不用于绩效，审计只记录行为与元数据。

#### Q-09 推送：飞书优先，邮件待定

项目现有架构以飞书消息卡片 + H5 为员工端，邮件不在 `.env.example` 和架构选型中。首期用飞书推送可以复用飞书身份、减少独立登录和 SMTP 配置；邮件推送列为 P2。若课程要求“邮件推送”为必做项，则需要补充 SMTP 配置、邮件模板和退信处理，并调整 FR-07 与里程碑。

#### Q-18 范围：P0 + Git，团队汇总建议做最小版

`proposal.md` §5 把“团队汇总”列为 P1，§12 的决策请求只承诺“P0 + Git 采集（P1）”，两处口径不一致。本报告建议：

- **必须交付**：P0 闭环 + Git 采集（P1）；
- **尽量交付**：团队汇总最小版（成员日报列表 + 阻塞项标记），不做复杂看板与排名；
- **不做**：邮件、周报/月报、模板管理、Jira/禅道、群聊采集、多语言；
- 若进度不足，团队汇总顺延到阶段二或后续迭代，并在 proposal 中明确。

## 4. 五个痛点与系统解法

| 痛点 | 现状 | 系统解法 | 对应功能 | 可度量验收 | 证据/验证方式 |
|---|---|---|---|---|---|
| 痛点 P1 回忆当天工作耗时 | 每天 10–30 分钟翻聊天、看提交、组织语言 | 自动采集当天工作痕迹，生成结构化草稿，员工只做确认/微调 | FR-02/03/04/05/06 | 生成 ≤5 秒（p95）；确认 ≤2 步；节省 ≥10 分钟/人/天 | 服务端埋点；试点问卷/访谈 |
| 痛点 P2 数据来源分散 | 日历、文档、任务、代码分布在不同系统，容易漏项 | 多源适配器 + 清洗聚合 + 来源引用 + 覆盖度提示 | FR-02/03/04 | 采集成功率 ≥95%；生成前可见数据覆盖度 | 任务日志；采集预览 |
| 痛点 P3 格式不统一 | 各人各写，模板执行靠自觉，管理者汇总困难 | 固定四段式模板 + 结构化输出 + schema 校验 + 字段开关 | FR-05/10 | 模板字段完整率 100%；格式错误率 <1% | 自动测试；样例评审 |
| 痛点 P4 日报形式化 | 内容空泛，缺少事实支撑，失去过程管理价值 | 事实约束 + 每条来源引用 + 人工确认 + 编辑留痕 | FR-05/06 | 采纳率 ≥60%；编辑字数占比 ≤30% | 编辑前后 diff 统计 |
| 痛点 P5 隐私顾虑 | 员工担心数据被用于绩效考核，抵触使用或敷衍 | 透明授权 + 字段级开关 + 单条排除 + 明确不用于绩效 + 审计 | FR-09 | 采集预览覆盖率 100%；退出/删除可用；相关投诉为 0 | 审计日志；试点问卷 |

> 对照关系：痛点 P1～P5 与 `docs/业务调研报告.md` §3.3 的痛点编号一致；每条解法都能追溯到功能编号和验收指标。

## 7. 冲突与取舍

| 编号 | 冲突 | 选项 A | 选项 B | 决策 | 理由 | 影响/复核 |
|---|---|---|---|---|---|---|
| C-01 | 采集完整度 vs 隐私 | 尽量多采集 | 最小必要采集 | 最小必要 + 透明 + 可排除 | 信任是使用率的前提；隐私风险高于少量漏项 | 采集预览；Q-06 |

## 9. 结论与下一步

### 9.1 结论

1. **需求成立**：日报是高频刚需，现有方案自动化程度低；“多源采集 + AI 草稿 + 人工确认 + 推送归档”的闭环有明确价值。
2. **范围可控**：本期以 P0 闭环 + Git 采集为必须；建议团队汇总做最小版，待评审确认；邮件、周报、模板管理、Jira/群聊列为 P2/后续。
3. **隐含需求清晰**：共整理 14 条隐含需求，其中 9 条直接影响 P0 验收，必须进入 spec。
4. **主要风险已识别**：飞书权限审批、数据合规表述、Git 身份映射、团队汇总范围、课程要求与项目选型的差异（数据库/邮件/Python 版本/群聊）。
5. **待确认项不影响启动**：O-01/O-02 可在第 1 周末前确认；其余可在第 2 周设计阶段闭环。
